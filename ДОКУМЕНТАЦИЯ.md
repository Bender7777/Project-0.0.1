# Проект «ОУКП — Реестр сотрудников»

Офлайн-приложение для отдела управления квалификацией персонала (ОУКП) департамента обслуживания на борту. Единый HTML-файл, работающий без интернета и сервера: реестр сотрудников с фильтрами, редактированием, генерацией листов ознакомления в Word и рассылкой писем.

---

## 1. Общее описание

**Что это.** `oukp.html` — самодостаточное одностраничное приложение (SPA) на чистом HTML/CSS/JavaScript без сборки и зависимостей от Node. Все данные, стили, скрипты, встроенный логотип и внешние библиотеки подключаются в одном файле. Открывается двойным кликом в любом современном браузере.

**Ключевые возможности:**
- Таблица сотрудников с 7 полями (ФИО, ФИО кратко, SAP-номер, эл. почта, функционал, дата рождения, ВРМ).
- Excel-подобные фильтры по каждой колонке (чек-листы уникальных значений) + глобальный поиск + сортировка.
- Инлайн-редактирование ячеек, добавление и удаление строк.
- Перетаскивание строк мышью для ручного порядка (drag-and-drop).
- Автосохранение между сессиями (гибридное хранилище — см. §5).
- Экспорт текущего вида в `.xlsx`.
- Генерация «Листа ознакомления» (ЛО) в формате `.docx` по выбранным сотрудникам, с автоподстановкой шапки, логотипа «Аэрофлот» и подписи начальника отдела.
- Рассылка письма выбранным сотрудникам через почтовый клиент по умолчанию (`mailto:`, адреса в поле «Кому»).

**Технологический стек:**
- Разметка/логика — нативные HTML/CSS/JS (ES2017+, async/await).
- `SheetJS (xlsx)` — чтение/запись Excel (подключается с CDN).
- `JSZip` — сборка `.docx` (это ZIP-архив с XML) на стороне браузера (CDN).
- Шрифты `IBM Plex Sans / Mono` (Google Fonts, CDN) — при отсутствии интернета откатываются на системные.
- Тёмная тема оформления, задаётся через CSS-переменные в `:root`.

## 3. Модель данных

### 3.1. Запись сотрудника

Каждый сотрудник — объект. Ключи полей на русском (как в исходном Excel), плюс служебный `id`:

```js
{
  id: "r5-a3f9k",                         // служебный уникальный ID (не из Excel)
  "ФИО": "Иванов Иван Иванович",
  "ФИО 2": "Иванов И.И.",                 // краткая форма — используется в ЛО и чипах
  "sap-номер": 12345,                     // число
  "эл.почта": "iivanov@aeroflot.ru",
  "Выполняемый функционал": "БПИ по ЛМР", // определяет цвет бейджа и поиск начальника
  "ДР": "1990-05-17",                     // ISO-формат YYYY-MM-DD
  "ВРМ": "VM-909-001234"                  // либо "X", либо пусто
}
```

### 3.2. Описание колонок — `FIELDS`

Массив-конфигурация, единый источник правды о колонках. Управляет и рендером таблицы, и формами редактирования, и экспортом:

```js
const FIELDS = [
  { key: 'ФИО',                    label: 'ФИО',           type: 'text',   cls: 'col-fio' },
  { key: 'ФИО 2',                  label: 'ФИО (кратко)',  type: 'text',   cls: 'col-fio2' },
  { key: 'sap-номер',              label: 'SAP-номер',     type: 'number', cls: 'col-sap' },
  { key: 'эл.почта',               label: 'Эл. почта',     type: 'email',  cls: 'col-email' },
  { key: 'Выполняемый функционал', label: 'Функционал',    type: 'text',   cls: 'col-func' },
  { key: 'ДР',                     label: 'Дата рождения', type: 'date',   cls: 'col-dr' },
  { key: 'ВРМ',                    label: 'ВРМ',           type: 'text',   cls: 'col-vrm' },
];
```

`type` определяет тип `<input>` при редактировании (`text`/`number`/`email`/`date`); `cls` — CSS-класс для стилизации ячейки.

### 3.3. Глобальное состояние (переменные модуля)

| Переменная | Тип | Назначение |
|-----------|-----|-----------|
| `records` | `Array` | Все записи сотрудников. Единственный массив-источник; порядок в нём = порядок отображения (до фильтров/сортировки). |
| `editingId` | `string \| null` | ID строки, редактируемой сейчас. |
| `newRowId` | `string \| null` | ID только что добавленной (ещё не сохранённой) строки. |
| `filters` | `Object` | Карта `ключ_колонки → Set разрешённых значений`. Отсутствие ключа = фильтр не активен. |
| `sortState` | `{ key, dir }` | Текущая сортировка: колонка и направление (`1` — по возрастанию, `-1` — по убыванию). |
| `globalQuery` | `string` | Строка глобального поиска. |
| `idCounter` | `number` | Счётчик для генерации ID. |
| `selectedIds` | `Set` | ID отмеченных галочками строк (для ЛО и рассылки). |
| `dragSrcId` | `string \| null` | ID перетаскиваемой строки (drag-and-drop). |
| `STORAGE_KEY` | `const string` | Ключ хранилища — `'oukp-records'`. |

## 4. Справочник функций

Функции сгруппированы по назначению. Для каждой указано: сигнатура, что делает, что возвращает.

### 4.1. Утилиты и идентификаторы

**`uid() → string`**
Генерирует уникальный ID строки вида `r{N}-{случайное}`. Инкрементирует `idCounter`. Применяется при загрузке данных и добавлении сотрудника.

**`withIds(arr) → Array`**
Принимает массив «сырых» записей (без `id`), возвращает копию, где каждой записи присвоен `uid()`. Используется при первичной загрузке `DEFAULT_DATA` и при сбросе к исходным данным.

**`escapeHtml(s) → string`**
Экранирует `& < > " '` для безопасной вставки текста в `innerHTML`. Защита от поломки вёрстки и XSS при отображении данных сотрудников.

**`formatDate(iso) → string`**
Преобразует ISO-дату `YYYY-MM-DD` в человекочитаемую `ДД.ММ.ГГГГ` для отображения в таблице. При некорректном вводе возвращает исходную строку (экранированную).

**`funcBadgeClass(val) → string`**
По значению поля «функционал» возвращает CSS-класс цветного бейджа: начальник/зам → `badge-chief`, главный специалист → `badge-spec`, БПИ → `badge-lead`, иначе → `badge-def`.

### 4.2. Хранилище и сохранение

**`hasClaudeStorage() → boolean`**
Проверяет, доступен ли объект `window.storage` (специальное хранилище среды Claude). Определяет, в каком режиме работает приложение — внутри интерфейса Claude или как отдельный файл. Ключевая функция гибридного хранилища (§5).

**`async loadRecords()`**
Загружает записи из подходящего хранилища при старте. Порядок: если есть `window.storage` — читает оттуда, иначе из `localStorage`. Если ничего не сохранено — инициализирует из `DEFAULT_DATA` (через `withIds`) и сразу сохраняет. Обёрнута в `try/catch` на случай недоступного хранилища.

**`async persist()`**
Сохраняет текущий массив `records` в подходящее хранилище (Claude storage или `localStorage`). Вызывается после каждого изменения данных. По итогу дёргает `flashSaveState()` для индикации в подвале.

**`flashSaveState(msg, isErr)`**
Показывает статус сохранения в подвале страницы (например «данные сохранены»/ошибка), затем через таймер возвращает нейтральный текст. `isErr` красит сообщение в цвет ошибки.

**`showToast(msg)`**
Показывает всплывающее уведомление (тост) внизу экрана на ~1,8 сек. Универсальный способ обратной связи по действиям (добавление, удаление, экспорт, ошибки выбора и т. п.).

### 4.3. Фильтрация, поиск, сортировка

**`uniqueValues(key) → Array`**
Возвращает отсортированный список уникальных значений заданной колонки по всем записям. Наполняет чек-лист в поповере фильтра.

**`applyFiltersAndSearch() → Array`**
**Центральная функция выборки.** Возвращает записи для отображения с учётом: активных фильтров колонок, глобального поиска и сортировки. Отдельно «закрепляет» редактируемую/новую строку (`newRowId`/`editingId`) — она всегда остаётся видимой сверху, даже если не проходит фильтр (иначе новая пустая строка исчезала бы — это был реальный баг, устранён).

### 4.4. Рендеринг таблицы

**`renderHead()`**
Строит `<thead>`: колонку-ручку для перетаскивания, колонку-чекбокс «выбрать все видимые», затем по `FIELDS` — заголовки с индикатором сортировки и кнопкой фильтра, и колонку «Действия».

**`inputForField(f, value) → string`**
Возвращает HTML `<input>` нужного типа (`text`/`number`/`email`/`date`) для поля `f` с текущим значением. Используется в режиме редактирования строки.

**`renderRowCells(row, isEditing) → string`**
Формирует HTML ячеек одной строки. В режиме просмотра — форматированные значения (бейдж функционала, дата `ДД.ММ.ГГГГ`, «X»/прочерк для ВРМ). В режиме редактирования — поля ввода из `inputForField`.

**`renderBody()`**
Рендерит `<tbody>` по результату `applyFiltersAndSearch()`: для каждой строки — ручка перетаскивания, чекбокс, ячейки, кнопки действий. Обновляет счётчики «показано/всего», бейджи выбранного (`updateLoBadge`, `updateEmailBadge`), переключает пустое состояние, ставит фокус в первое поле редактируемой строки.

**`render()`**
Полная перерисовка: `renderHead()` + `renderBody()`. Вызывается после любого изменения состояния.

### 4.5. Редактирование, добавление, удаление

**`startEdit(id)`**
Переводит строку в режим редактирования. Если уже редактировалась другая — тихо коммитит её. Ставит `editingId` и перерисовывает.

**`collectRowInputs(id) → Object`**
Считывает значения всех полей ввода редактируемой строки в объект. Числовые поля приводит к `Number`. Возвращает данные для сохранения.

**`async commitEdit(id, silent)`**
Сохраняет изменения строки: собирает поля через `collectRowInputs`, обновляет запись в `records`, сбрасывает `editingId`/`newRowId`, вызывает `persist()` и `render()`. При `silent=false` показывает тост («Сотрудник добавлен»/«Изменения сохранены»).

**`async cancelEdit(id)`**
Отменяет редактирование. Если строка была новосозданной (`newRowId`) — удаляет её из `records`. Сбрасывает флаги и перерисовывает.

**`async addRow()`**
Добавляет нового сотрудника: коммитит текущее редактирование, создаёт пустую запись со всеми полями `FIELDS`, вставляет в начало `records`, переводит её в режим редактирования и сбрасывает поиск, чтобы строка была видна.

**`requestDelete(id)`**
Открывает модальное окно подтверждения удаления с именем сотрудника. Запоминает ID в `pendingDelete`.

**`async confirmDelete()`**
Подтверждённое удаление: убирает запись из `records`, чистит её из `selectedIds`, сохраняет и перерисовывает.

**`requestReset()`**
Открывает подтверждение сброса всех данных к исходному Excel.

**`async confirmReset()`**
Сброс: заново инициализирует `records` из `DEFAULT_DATA`, очищает выбор, фильтры и флаги редактирования, сохраняет, перерисовывает.

### 4.6. Поповер фильтра колонки

**`closePopover()`**
Закрывает открытый поповер фильтра, сбрасывает `openFilterKey`.

**`openPopoverFor(key, anchorBtn)`**
Открывает поповер фильтра для колонки `key` рядом с кнопкой `anchorBtn`. Строит: поиск по значениям, «выделить/снять всё», чек-лист (`uniqueValues`), кнопки «Сбросить»/«Применить». По «Применить» — если выбраны все значения, фильтр снимается; иначе в `filters[key]` кладётся `Set` выбранных. Позиционируется под кнопкой.

### 4.7. Лист ознакомления (генерация `.docx`)

**`updateLoBadge()`**
Обновляет счётчик на кнопке «Создать ЛО» по числу `selectedIds`. Скрывает бейдж при нуле.

**`findDeptHead() → string`**
Ищет в `records` начальника отдела (по слову «начальник отдела» в функционале), возвращает его краткое ФИО. Используется для автоподписи в ЛО.

**`selectedRecords() → Array`**
Возвращает записи из `records`, чьи ID есть в `selectedIds`. Общий помощник для ЛО и рассылки.

**`renderLoChips()`**
Рендерит «чипы» выбранных сотрудников в модалке ЛО с кнопкой удаления из списка. Обновляет счётчик выбранных.

**`openLoModal()` / `closeLoModal()`**
Открывают/закрывают модалку создания ЛО. При открытии требуют хотя бы одного выбранного (иначе тост-предупреждение) и рендерят чипы.

**`loFormatDate(iso) → string`**
Форматирует дату документа `YYYY-MM-DD → ДД.ММ.ГГГГ` для шапки ЛО. (Аналог `formatDate`, отдельный для контекста генерации.)

**`escXml(s) → string`**
Экранирует спецсимволы для вставки в OOXML (`& < > " '`). Обязателен для корректного XML в `.docx`.

**`xmlPara(text, opts) → string`**
Собирает XML-абзац (`<w:p>`) Word с параметрами: выравнивание по центру, жирность, размер шрифта, отступ. Базовый кирпич для сборки тела документа. Шрифт — Times New Roman.

**`buildLoDocumentXml(data) → string`**
**Сердце генератора.** Собирает полный `word/document.xml` листа ознакомления: верхнюю таблицу-шапку (логотип «Аэрофлот» слева, название формы по центру, код `ЗК-ГД-012B` и «Стр. 1 из 1» справа), заголовок с реквизитами (`номер «название» № КАСУД от дата`), основную таблицу со списком выбранных сотрудников (№, ФИО, должность, пустые «Дата»/«Подпись» под роспись + пустые строки), блок подписи начальника и опциональный блок «Исп./Тел.», а также колонтитул. Возвращает XML-строку.

**`loCoreXml(title) → string`**
Формирует `docProps/core.xml` (метаданные документа — заголовок, даты создания/изменения).

**`async generateLoDocx()`**
**Оркестратор экспорта ЛО.** Читает реквизиты из формы, валидирует обязательные поля (подсвечивает пустые), берёт выбранных сотрудников, определяет подпись через `findDeptHead()`, вызывает `buildLoDocumentXml()`. Затем через `JSZip` собирает валидный `.docx` (Content_Types, rels, document.xml, footer, media/logo.png, docProps) и запускает скачивание файла `ЛО_{номер}.docx`. Обрабатывает ошибки тостом.

### 4.8. Рассылка писем

**`updateEmailBadge()`**
Обновляет счётчик на кнопке «Письмо выбранным» по числу `selectedIds`.

**`renderEmailChips()`**
Рендерит чипы получателей в модалке письма. Помечает и подсчитывает тех, у кого нет адреса эл. почты (они не попадут в письмо), с кнопкой удаления из списка.

**`openEmailModal()` / `closeEmailModal()`**
Открывают/закрывают модалку письма. При открытии требуют хотя бы одного выбранного и рендерят чипы.

### 4.9. Константы-шаблоны OOXML

Строковые константы с готовыми частями `.docx`-архива:

| Константа | Что содержит |
|-----------|--------------|
| `LO_CONTENT_TYPES` | `[Content_Types].xml` — регистрация типов частей (в т.ч. PNG). |
| `LO_RELS` | `_rels/.rels` — корневые связи пакета. |
| `LO_DOC_RELS` | `word/_rels/document.xml.rels` — связи документа (колонтитул + изображение логотипа). |
| `LO_FOOTER` | `word/footer1.xml` — колонтитул со ссылкой на проверку актуальности (qms/kasud). |
| `LO_APP_XML` | `docProps/app.xml` — расширенные свойства. |
| `LOGO_PNG_BASE64` | Логотип «Аэрофлот» в Base64 (встроен, работает офлайн). |

## 5. Гибридное хранилище (важный архитектурный момент)

Приложение может быть открыто **двумя способами**, и в каждом доступно своё хранилище:

1. **Внутри интерфейса Claude** (предпросмотр артефакта) — доступен только `window.storage` (серверное хранилище Claude). `localStorage` может не работать.
2. **Как скачанный файл на ПК** (двойной клик) — `window.storage` отсутствует, доступен `localStorage` браузера.

Функция `hasClaudeStorage()` определяет режим, а `loadRecords()`/`persist()` выбирают правильное хранилище автоматически. Это решает баг «данные не сохраняются», который возникал, когда использовалось только одно из хранилищ.

**Практическое следствие для пользователя:** при работе с файлом на ПК данные привязаны к конкретному браузеру и расположению файла. Нельзя перекачивать копию заново (получите пустой/исходный реестр) — файл нужно держать в одном месте и открывать из него же. Для многопользовательской синхронной работы этот механизм не предназначен.

## 6. Пользовательские сценарии (как это работает)

**Фильтрация:** клик по иконке-воронке в заголовке колонки → чек-лист значений → «Применить». Несколько фильтров работают вместе (логическое И). Глобальный поиск — по всем полям одновременно.

**Редактирование:** двойной клик по ячейке (или кнопка-карандаш) → правка полей → `Enter` сохраняет, `Esc` отменяет.

**Добавление:** «Добавить сотрудника» → пустая строка сверху в режиме правки → заполнить → сохранить.

**Порядок строк:** тянуть за ручку (⋮⋮) слева. Ручной порядок сбрасывает сортировку по колонке.

**Лист ознакомления:** отметить сотрудников галочками → «Создать ЛО» → ввести 4 реквизита (номер документа, название, № КАСУД, дата) → «Сформировать .docx». Подпись начальника и логотип подставляются автоматически.

**Письмо:** отметить галочками → «Письмо выбранным» → тема/текст → «Открыть почтовый клиент». Адреса подставляются в поле «Кому» (все получатели видят друг друга). Откроется тот клиент, что назначен в Windows по умолчанию (например RuPost — его нужно назначить почтовым клиентом по умолчанию через настройки самого RuPost, т.к. клиенты на базе Thunderbird регистрируются в системе изнутри приложения).

## 7. Подробный план разработки

План рассчитан на продолжение работы в режиме Claude Code. Разбит на фазы; внутри каждой — конкретные задачи и критерии готовности. Порядок отражает приоритет: сначала устойчивость и структура, затем функции, затем полировка.

### Фаза 0. Подготовка репозитория
- [ ] Инициализировать git-репозиторий, добавить `.gitignore` (node_modules, временные файлы).
- [ ] Поместить `oukp.html` как baseline, зафиксировать первый коммит («рабочая версия до рефакторинга»).
- [ ] Добавить `README.md` с краткой инструкцией запуска и `ДОКУМЕНТАЦИЯ.md` (этот файл).
- [ ] Сохранить исходники (`ОУКП.xlsx`, `Рисунок.png`, `РИ-ГД-267А.docx`) в папку `source/`.
- **Готово, когда:** репозиторий собран, история начата, исходный файл открывается и работает.

### Фаза 1. Рефакторинг в модульную структуру
- [ ] Вынести `<style>` в `css/styles.css`.
- [ ] Разбить единый `<script>` на модули из §2 (config, storage, state, table, editing, dragdrop, filters, export-xlsx, lo-docx, email, main). Использовать ES-модули (`type="module"`) или простую конкатенацию при сборке.
- [ ] Вынести логотип в `assets/logo.png`; предусмотреть Base64-встраивание на этапе сборки (для офлайн-версии).
- [ ] Написать простой скрипт сборки (`build`) — конкатенация/инлайнинг в единый `build/oukp.html`. Подойдёт Node-скрипт или Vite с `vite-plugin-singlefile`.
- **Готово, когда:** собранный `build/oukp.html` идентичен по функциональности исходному, но код разбит на модули; ни одна функция не потеряна.
- **Проверка:** прогнать все сценарии §6 в браузере (headless Playwright), сверить с baseline.

### Фаза 2. Надёжность данных
- [ ] Валидация полей при вводе: e-mail (формат), SAP-номер (целое, уникальность), дата (диапазон). Подсветка ошибок без блокировки работы.
- [ ] Импорт из `.xlsx`: кнопка «Импорт», чтение файла через SheetJS, сопоставление колонок, слияние/замена реестра с подтверждением.
- [ ] Экспорт: убедиться, что выгружается полный реестр (а не только видимый), добавить опцию «только видимые/все».
- [ ] Резервная копия: экспорт/импорт всего состояния в JSON (бэкап и перенос между браузерами) — решает ограничение localStorage из §5.
- [ ] Обработка переполнения localStorage (квота ~5 МБ) — предупреждение и предложение бэкапа.
- **Готово, когда:** данные нельзя потерять по неосторожности; есть перенос между машинами через JSON/Excel.

### Фаза 3. Функции листа ознакомления
- [ ] Шаблоны ЛО: сохранять часто используемые реквизиты (название формы, исполнитель, телефон) в хранилище, подставлять по умолчанию.
- [ ] Проверка орфографии реквизитов и предпросмотр шапки прямо в модалке до генерации.
- [ ] Опция числа пустых строк в таблице ЛО (сейчас фиксировано 2).
- [ ] Поддержка нескольких листов/страниц при большом числе сотрудников (корректная разбивка).
- [ ] Автотест генерации: собрать `.docx`, открыть через LibreOffice headless, проверить, что таблицы, логотип и подпись на месте (как делалось при разработке).
- **Готово, когда:** ЛО генерируется под разные документы без ручной правки XML, генерация покрыта автотестом.

### Фаза 4. Рассылка и интеграции
- [ ] Проверка длины `mailto:` (лимит ~2000 символов в некоторых клиентах); при большом числе адресов — разбивка на несколько писем или предупреждение.
- [ ] Шаблоны писем: сохранять типовые тема/текст.
- [ ] Инструкция-подсказка по назначению RuPost клиентом по умолчанию прямо в UI (ссылка/тултип).
- [ ] Опционально: экспорт списка адресов в файл (для вставки в клиент вручную, если mailto недоступен).
- **Готово, когда:** рассылка работает при любом числе выбранных, пользователь понимает, как настроить RuPost.

### Фаза 5. UX и доступность
- [ ] Клавиатурная навигация по таблице (стрелки, Tab), горячие клавиши (добавить строку, поиск).
- [ ] Пагинация или виртуализация при росте реестра (сейчас все строки в DOM).
- [ ] Массовые операции: удалить/снять выбор, массовое редактирование функционала.
- [ ] Адаптив под мобильные/планшет (таблица горизонтально скроллится — проверить удобство).
- [ ] Индикаторы загрузки/сохранения, аккуратные пустые состояния.
- **Готово, когда:** приложение комфортно при 100+ сотрудниках и с клавиатуры.

### Фаза 6. Качество и поставка
- [ ] Юнит-тесты чистых функций (форматтеры, фильтры, сборка XML) — Vitest/Jest.
- [ ] E2E-тесты сценариев (Playwright): добавление, редактирование, фильтр, drag-drop, генерация ЛО, письмо.
- [ ] Линтер (ESLint) и форматтер (Prettier), единый стиль.
- [ ] Финальная сборка единого офлайн-файла, проверка работы без интернета (CDN-библиотеки инлайнить или заменить на локальные).
- [ ] Обновить `ДОКУМЕНТАЦИЯ.md` и `README.md` под новую структуру.
- **Готово, когда:** есть зелёные тесты, единый офлайн-билд работает без сети, документация актуальна.

### Технический долг / известные ограничения
- CDN-зависимости (SheetJS, JSZip, шрифты) требуют интернета при первой загрузке — для полного офлайна их нужно инлайнить в билд.
- `localStorage` привязан к браузеру и пути файла; нет синхронизации между пользователями (осознанное ограничение офлайн-инструмента).
- Все строки рендерятся в DOM — при очень больших реестрах нужна виртуализация (Фаза 5).
- `mailto:` ограничен по длине и зависит от настроенного клиента по умолчанию.
